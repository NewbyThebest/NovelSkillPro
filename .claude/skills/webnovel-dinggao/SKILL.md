# 定稿回写

## 目标与路径

用户确认章节定稿后，先确认最新正文与章纲的关系，再将这份正文作为后续维护的唯一事实来源。完成本章归档、控制台更新和必要的规划维护后，等待用户进入下一章，不自动继续写作。

- 将本技能目录记为 `SKILL_DIR`，包含 `.agents/` 的项目根目录记为 `WORKSPACE_ROOT`。
- 小说文件从 `WORKSPACE_ROOT` 读取和写入；模板从 `<SKILL_DIR>/references/` 的实际绝对路径读取。
- 已确认的定稿、控制台状态和已回写章纲不得被后续草稿覆盖。

## 步骤 0：定位章节与定稿前对齐

先执行控制台门槛：第一次章节定稿时必须创建 `控制台/时间线.md`、`控制台/地图.md` 与 `控制台/主角能力与资源.md`，以后每次定稿都必须读取并核对。文件缺失时，若项目已有定稿，先依据全部既有定稿重建，不能只从最新一章反推；若正在处理第一章定稿，则从本章定稿事实建立。时间线无法精确到日时保留相对时段，不得自行补日期；地图无法确认的方向、出口、距离和区域关系一律不写入，不得自行补成客观地图。没有持续动态资产时也不能省略总账，在“当前概况”写“当前无需要追踪的动态资产”，各事实分区写“无已定稿项目”。无法判断时继续核对正文事实，不得把不确定当作无资产或已确认空间。

1. 结合用户明确说明、当前对话、`4-正文/` 中的 `第X章_草稿_[标题].md` 或 `第X章_定稿_[标题].md`、以及 `控制台/进度.md` 定位待处理章节。
   - 上下文、文件和进度能指向同一章时继续。
   - 存在多个候选、章节号冲突或用户未说明时，停止并只问“要为第几章定稿？”。
2. 长篇模式按本章章号找到 `3-大纲/` 下对应的十章章纲文件。第 1—10 章使用 `章纲_1-10章.md`，第 11—20 章使用 `章纲_11-20章.md`，后续依此类推；文件名固定，不根据剧情目标或实际收束情况调整。`SHORT_STORY_MODE` 下读取 `3-大纲/短篇章纲.md`。读取其中本章章纲与待定稿正文。
3. 在重命名前做只读对齐：确认正文是否改变了本章核心事件、角色状态、伏笔、结尾状态或设定事实。
   - 无实质差异，或用户明确以当前正文为准时，继续转正。
   - 存在实质差异时，向用户列出“章纲 vs 正文”的事实差异，并让用户选择：按正文回写章纲，或先返回草稿修正。选择修稿时不转正、不更新控制台。
   - 本章新写出的规则、地点、机制或人物细节，只要不与已定稿正文互相矛盾，就直接按正文处理，不记作差异、不改设定。只有两者无法同时成立时，才按步骤 4 向用户提出。
4. 本章涉及主要角色或核心关系时，读取 `2-设定/2.3_主要角色设定表.md` 或 `2-设定/2.3.2_核心关系.md` 的相关条目；出现、复用或结算阶段角色时，读取 `2-设定/2.3.1_阶段与功能角色记录.md` 的相关条目，判断正文产生的是短期状态还是稳定档案变化。当前文件的低频归档索引指向本章复用角色时，再读取对应 `2-设定/角色归档/[阶段名].md` 条目，不加载无关归档。
5. 读取 `控制台/时间线.md`，核对事实截止、当前时间锚点、相邻事件间隔、持续时长、期限与倒计时。本章正文出现“次日”“数日后”“第X日”、具体时辰或倒计时时，必须确认起点和跨度能被既有定稿支持；无法精确换算时保留原文相对时间并记入不确定项，不得补成绝对日序。
6. 读取 `控制台/地图.md`，核对本章涉及的区域、地点、已确认连通关系、局部方向、通行条件、监控或权限限制。地图只保存跨章复用的空间结构；人物当前地点仍写入进度和角色状态，本章逐步走位仍以正文为准。
7. 读取 `控制台/主角能力与资源.md`，核对当前概况、事实截止和实际条目。第一章定稿时必须创建并从本章定稿事实填写；已有多章定稿但总账缺失时，必须先追溯全部定稿，重建截至最新章的当前动态资产。每次定稿都要核对总账，即使本章没有资产变化也不能跳过；本章首次出现需要跨章节核对的资产时，更新当前概况并纳入对应事实分区。
8. 用户确认以该正文定稿后，先执行中文标点与引号自动校准，再转正。这是**不得跳过的强制步骤**：无论是否认为正文标点和引号已正确，都必须实际运行脚本，不得凭判断省略或声称“已检查”。在 `WORKSPACE_ROOT` 下执行：

   ```bash
   python "<SKILL_DIR>/scripts/fix_quotes.py" --fix "<WORKSPACE_ROOT>/4-正文/第X章_草稿_[标题].md"
   ```

   将占位符替换为实际绝对路径和章节号。脚本按 `AGENTS.md` 统一修正英文半角句读、括号、破折号、省略号和错误引号，并交换左右写反的引号对；Markdown 代码、链接、网址、路径、小数与列表标记受保护。脚本报告修复后仍不配对的引号位置时，先说明并确认处理方式，再继续转正。随后将 `第X章_草稿_[标题].md` 重命名为 `第X章_定稿_[标题].md`，只替换状态字段并保留章节标题。标题在定稿前已经变更时，使用用户最新确认的安全文件名标题，不保留旧标题副本；用户已手动转正时直接使用定稿文件。正文内容从故事第一句开始，不在文件内重复章号或标题。
9. 若该章已经是定稿，且 `控制台/进度.md` 已记录为完成，默认视为已收尾，不重复更新。只有用户明确要求修复、补回写或重新结算时才继续。

## 步骤 1：回写本章章纲

以定稿正文为准更新本章章纲的事实描述：剧情骨架、读者回报或蓄势、伏笔线索和结尾状态。

- 回写剧情骨架时，定稿正文只用于确认已发生的事实，不按正文段落、动作链或场景镜头复述。
- 剧情骨架必须使用 Markdown 有序列表。每个列表项对应一次独立的局面变化，只写发生什么、谁作何选择、造成什么结果。
- 同一场连续行动中，若中途没有新的选择、信息或局面变化，应合并为同一项，不按动作先后拆成多项。
- 不回填具体台词、连续动作、招式过程、走位、现场反应、环境描写或情绪节拍，除非该细节本身改变后续剧情边界。
- 定稿正文与剧情骨架只需在事件顺序、人物选择、结果和已确认事实上一致。
- 只更新已被用户确认接受的正文差异，不反向改写定稿正文。
- 本章章纲缺失时，基于定稿正文补建最小可用记录，不补造未写出的剧情。
- 本章存在“创作原料（定稿前临时保留）”时，只有在正文转正且事实章纲回写完成后才删除该节。草稿生成、审查、润色或用户尚未确认定稿时不得提前清理。
- 没有写进定稿正文的创作原料默认不成为事实。用户明确要求留到后续时，先确认去向，再转入下一章创作原料或尚未写出的规划；不得自动写入控制台、角色档案或伏笔记录。
- 回写完成后说明本章章纲是否有改动，以及改动的事实范围。

## 步骤 2：更新控制台

首次定稿时，若 `控制台/时间线.md`、`控制台/地图.md` 或 `控制台/主角能力与资源.md` 缺失，从 `<SKILL_DIR>/references/` 复制对应模板到 `控制台/`，删除模板提示后填写真实项目事实。时间线、地图与总账每个项目都必须存在。已有多章定稿但文件缺失时，先追溯全部定稿重建，不只记录本章变化；无法精确换算的时间不写入时间线，无法确认的空间关系不写入地图。总账有动态资产时在“当前概况”概括资产类型，并登记当前事实；当前没有需要追踪的动态资产时，在“当前概况”写“当前无需要追踪的动态资产”，保留各分区并写“无已定稿项目”。

每次定稿后按以下规则更新。**每个控制台文件只记录本表规定的本职内容，其余一律不写入**；不确定某个事实该归哪个文件时，宁可少记，也不要重复记进多个文件。

| 文件 | 更新规则 |
| :--- | :--- |
| `控制台/时间线.md` | 每章必更：事实截止、当前时间锚点、本章造成的时间段推进。只保留时间锚点与关键事件；期限倒计时、约定与无法换算的时间粒度不写入本文件。 |
| `控制台/进度.md` | 每章必更：当前承接、最近三章、下一步与阶段缺口。 |
| `控制台/角色状态.md` | 按需更新。**只追踪 `2.3_主要角色设定表.md` 中已建档的主要角色**；阶段与功能角色、未揭身份的路人、只承担场景作用的角色不写入。没有变化且仍属当前工作集时保留，不再影响当前阶段创作时删除。 |
| `控制台/主角能力与资源.md` | 每个项目必有；首次定稿创建，之后每章定稿都核对当前概况、事实截止和事实条目。只记录主角的状态、层级、境界、能力、资源与物品；伤势、认知归角色状态，悬念归伏笔追踪，时间归时间线，空间归地图，不在此重复。资产发生变化时重建当前条目；没有动态资产时保留明确的无资产事实，不能因本章没有变化而跳过。 |
| `控制台/地图.md` | 每章核对；本章新增或确认跨章复用的区域、地点、连通关系、空间限制、方向、监控或权限事实时更新。只把定稿正文已确认的空间事实写入；猜测、未验证出口和用途不明区域不写入本文件，等正文确认后再补入；没有空间变化时保留原记录。 |
| `控制台/伏笔追踪.md` | 每章必审：新埋、推进、收回的伏笔发生变化时更新。**只有一张待收回表**，伏笔收回后直接删除、不移入已收回表。必须逐条对照待收回列表执行收回判定，不得只增不减。 |

所有记录只写正文已经发生的事实，不把下一章计划写成已发生状态，不把猜测写成伏笔结论或已确认空间。完成后明确列出本次实际更新的控制台文件和条目。

### 伏笔追踪维护规则

`控制台/伏笔追踪.md` 只记录真正的伏笔。**伏笔的定义**：正文中已经写下的、指向未来才会揭晓的可验证线索，必须同时满足三条——

1. 正文实写了这件事，不是作者的规划或角色的猜测；
2. 它是明确的谜团、阴谋、机制暗线或未决危机；
3. 它现在无法被读者自行回答，需要后续正文给出答案。

不符合这三条的不得写入本表。**明确排除**：人物之间的信任建立、感情变化、日常对话与关系推进；已经交代清楚的事实；读者当场就能推断出结论的写法；角色的常规反应、神态、态度等一次性描写；情绪起伏、状态描述与生活细节。诸如“某人记住了某人的镇定”这类没有指向具体谜团的描写，属于角色刻画而不是伏笔。

**本表只有一张《待收回伏笔》表。** 伏笔收回之后直接从本表删除，不移入“已收回伏笔”表——收回之后它已经是定稿正文与章纲里的既成事实，再留一张表只会让本文件随章节数无限增长。需要回查某条旧伏笔在哪一章收回，去看对应章纲。线索链与关系发展线也不写入本文件：线索链由十章章纲与定稿正文承担，人物关系由定稿正文、角色设定与角色状态承担。

**备注列只写事实边界**：这条伏笔在正文里写到了哪一步、还差什么没交代、复用时不得自行补什么。不写角色做了什么、说了什么、过程如何——那些是定稿正文和章纲的内容。备注控制在两句话以内，超过一百二十字基本就是把剧情过程抄进来了。

每章定稿时按以下规则维护：

1. **逐条过筛（强制）**：对照“待收回伏笔”列表逐条自问：
   - ① **初始谜团是否已解**：本章是否已经给出了该伏笔埋设时的核心答案（去向已查明、身份已揭晓、规则已验证）？
   - ② **是否达成阶段性闭环**：该事件的初始危机或任务是否已告一段落？
   - ③ **是否已衍生为全新事件**：旧悬念是否已解决并转化为新的明确目标？若已转化，旧条目必须收回，新目标按需另立条目。
   - ④ **是否根本不算伏笔**：若该条目只是人物日常互动、常规反应或已经说明清楚的事实，直接删除，不转入任何其他分节。

2. **收回即删除**：只要某个伏笔在正文中获得了明确的事实印证或阶段性闭环，哪怕它背后牵扯更大的长线主线，也必须立即判定为已收回，**从表中删除该行**，不移入任何其他表。不得以“这层背景还没交代完”为由，把早已查明的阶段性谜团无限期堆在表里。

3. **不得只增不减**：每章都要真正执行收回判定，保持本表聚焦于当前及近端的核心悬念。表只会因为新埋伏笔而增加行数，旧行必须随收回而减少。

每次定稿后运行：

```bash
python <SKILL_DIR>/scripts/validate_foreshadowing.py <WORKSPACE_ROOT>
```

校验未通过时先修正再继续。脚本不可用时，至少人工确认：文件里只有《待收回伏笔》一张表；每行都有伏笔内容、埋设章节、预期收回与备注；备注只写事实边界且不超过两句话；已经收回的条目确实已从表中删除。

### 地图文件维护规则

`控制台/地图.md` 是唯一可跨章复用的空间事实账，不是人物位置表、逐章走位记录、完整世界百科，也不是未确认空间的暂存处。始终按 `<SKILL_DIR>/references/地图模板.md` 的结构维护：

1. **四张表，只写四列封顶**：区域索引、地点索引、已确认连通关系、空间限制与通行条件。全文件只保留维护边界里那一行“事实截止”用于核对最新定稿章。
2. **事实截止与区域边界**：每章定稿后更新到最新定稿章节；区域索引只收录已确认的区域层级与稳定功能，不补完整地图。
3. **地点与连通关系**：地点索引只收录会影响后续行动的稳定节点；连通关系必须标明行进参照与通行条件，不能把一次性走位扩成坐标或绝对方位。
4. **只写空间，不做推演**：只写“这里是什么、怎么通、有什么拦着”，不写“因此会怎样”。像“屋内动静会被门外听见”“被逼到台边即无退路”这类影响与后果，留给章纲和正文判断，地图不为它们单列。
5. **空间限制**：只收录会改变后续选择且尚未在别处写明的空间限制。同一节点的多条限制合并成一行，不重复单列；比赛规则、判定与扣分、系统播报、身份等级、作息安排、环境描写一律不写入。
6. **未确认空间不入账**：疑似出口、用途不明房间、未验证路线、角色推断与不完整方位一律不写入本文件，等正文确认后再补进已确认表。
7. **职责边界**：人物当前地点写入进度和角色状态；移动耗时写入时间线；本章具体走位、人物去向与人物反应留在正文与章纲；地图只保留稳定空间结构。

每次定稿后运行：

```bash
python <SKILL_DIR>/scripts/validate_map.py <WORKSPACE_ROOT>
```

地图校验未通过时先修正地图再继续。脚本不可用时，至少人工确认：维护边界里的事实截止等于最新定稿；四张表没有多出 ID、状态或事实依据列；没有引用尚未定稿章节；没有为未确认的空间事实建账；没有写进比赛规则、系统机制、身份等级、作息安排、环境描写或人物动态位置；没有超出“这里是什么、怎么通、有什么拦着”去写影响与后果。

### 时间线文件维护规则

`控制台/时间线.md` 是唯一故事时间事实账，不是逐章剧情摘要，也不是期限跟踪表。始终按 `<SKILL_DIR>/references/时间线模板.md` 的结构维护：

1. **事实截止与当前锚点**：每章定稿后更新到最新定稿章节，写清当前相对时段、当前事件所处时间位置和最近明确时长。无法确定绝对日期或入园第几天时必须直写“无法确认”。
2. **已定稿时间段**：按连续时间段合并章节，每个时间段只写一句话，只写“什么时候、在哪里、发生了什么”这层时间骨架。例如“主角中午签下合同，傍晚抵达目的地，入夜被推上场连打两场，之后押入住处”。招式名、能力名、战绩、身份晋升、资源得失、人物关系与情绪节拍一律不写入本文件——它们分别属于总账、章纲和角色状态。一句话里也不得展开逐章剧情、对白或招式过程。
3. **只记时间骨架**：倒计时、约定、治疗周期与巡查规律由定稿正文、章纲与进度中的“即时未决”承接；正文没有明确写出的时长、间隔与先后关系一律不入账，等正文确认后再补入。不得自行换算成固定天数，也不得把多个可能重叠的时段机械相加。
4. **时间冲突处理**：若本章时间词与旧定稿无法同时成立，先列出冲突并让用户确认，不静默改正文或旧时间线；用户明确以当前正文为准后，才按正文回写受影响的时间段。
5. **职责边界**：时间线只管已定稿时间段里的时间跨度与事件先后。当前地点、章尾局面和下一步写入进度；角色即时状态、伤势与认知写入角色状态；能力、资源与物品写入动态资产总账；空间结构写入地图；剧情过程写入章纲。

### 角色状态文件维护规则

`控制台/角色状态.md` 是下一章直接读取的动态工作表，不是已登场角色名册或逐章档案。始终按 `<SKILL_DIR>/references/角色状态模板.md` 的结构维护：

5. **只写事实，不写解读**：写人物做了什么、说了什么、处在什么状态，不写“这说明他并不接受某套说法”这类推断与评价。

### 主角动态资产总账维护规则

`控制台/主角能力与资源.md` 是每个项目首次定稿时必须建立的唯一主角动态事实总账。**只记录主角的状态、层级、境界、能力、资源与物品**；伤势与认知归角色状态，未收悬念归伏笔追踪，时间归时间线，空间归地图，一律不在此重复。始终按 `<SKILL_DIR>/references/主角能力与资源模板.md` 的职责维护：

2. “当前概况”一句话概括已在表内的资产类型（凭证、机制、手段、物资等，不必逐项列举）；当前没有动态资产时写“当前无需要追踪的动态资产”。以后首次出现需要跨章节核对的资产时，更新概况并补记。
3. **核心机制用字段，具体招法走表格**。长期规则（承技条件、化法原则、反哺机制）用「#### 机制名称」加“作用／限制”两项写清。**一个机制只有一条：它的派生信息并进该机制自己的字段里，不另立条目**——例如某种机制自带的一行口诀或提示，写进该机制自己的字段，不单开一条同名条目。具体招法一律写进「### 当前手段」表，一行一门、四列（手段／类型／作用／限制），每格一两句，**不得为每一门招法单独建标题和字段**——招法随承技次数线性增长，字段式写法会让本文件无限膨胀。
4. **收录门槛：只收会影响后续战斗、交易、身份、通行或暴露风险的资产**——能改变战斗力的物资、能决定通行与权限的凭证、能牵动身份与暴露的证据。**日常饮食起居不收录**（饭食、铺盖、洗漱用品等）：这类东西会持续获得，正文也不会专门交代它们被消耗，收进表里只会永远挂在表上。正文明确写到某件东西的使用、交易或耗尽时，才补入或删除对应行。
5. **只写“有什么、能做什么”**。物品只记名称、数量、位置三样。**不写用途、疗效、限制说明与横向对比**：某件东西抹上去什么感觉、比平时伙食好了多少、能换什么，属定稿正文、章纲与设定案的职责，本文件不复制。招法只写作用与限制，不写它是在哪一场怎么打出来的。
6. **已经用尽或不再持有的东西直接从表里删掉**。
7. 新获能力、能力改名、融合、失效或限制变化时，覆盖对应行或条目。**已经并入其他招式的能力不单列**，只在并入后的那一条里用一句话说明来源。
8. 正文未明确数量时写“数量未核定”或“至少”，不能因近期没提便记为零。
9. 未定稿章纲、创作原料和用户尚未落实到正文的未来奖励、消耗、突破或装备变化不得提前入账。事实截止必须更新为最新定稿章节，即使本章没有发生动态资产变化。
10. 角色的伤势与认知写入角色状态，长期未决问题写入伏笔追踪，时间写入时间线，空间写入地图，均不在本文件重复。

### 进度文件维护规则

`控制台/进度.md` 是供下一章直接使用的动态工作台，不是逐章档案，也不是成果汇总。始终按 `<SKILL_DIR>/references/进度模板.md` 的三段结构维护：

## 步骤 4：一致性审计与按需规划修订

不在每章自动改总纲或设定。以下情况才触发复盘：

- 本章正文与已定稿正文、稳定设定或总纲**互相矛盾**（两者无法同时成立）。单纯新增的规则、地点、机制与人物细节不触发复盘。
- 当前阶段的完成标志已经达成。
- 定稿正文持续偏离当前总纲的阶段方向、读者承诺或硬约束。
- 本章定稿后累计到第 10、20、30 章等十章节点（此时向用户询问是否做全项目一致性审计，不直接执行）。
- 用户明确要求核对正文与预期、设定、大纲、控制台之间的出入。
- 用户明确要求调整后续规划。

**每十章定稿后，向用户询问是否进行全项目一致性审计。** 询问不等于执行：到达十章节点时，先照常做本章定稿回写与常规控制台更新，然后在收尾交付里问一句“已到十章节点，要不要做一次全项目一致性审计”，等用户明确同意再执行。用户没有表示时，不得自行拉起审计、不得为此启动子代理、也不得把审计结论写进交付。

### 全项目一致性审计（每十章定稿后询问用户是否执行）

**每十章定稿后，向用户询问是否进行全项目一致性审计，用户同意后再执行；用户没有表示时不得自行拉起审计。** 用户在非十章节点明确要求全面检查时也执行本节。执行时同时做事实一致性审计与剧情方向审计，不能只检查十章章纲。用户未指定范围时，核对当前全部定稿正文。

#### 审计范围与事实源

1. 读取刚完成十章范围内的全部定稿正文，以正文中实际发生的内容作为事实源。当前文件引用了更早事实时，继续读取对应的早期定稿章节，不能凭控制台或记忆反推正文。
2. 读取当前项目中的全部 `1-预期/*.md`、`2-设定/*.md`、`3-大纲/*.md` 和 `控制台/*.md`，其中必须用 `控制台/时间线.md` 核对事件顺序与跨日，用 `控制台/地图.md` 核对区域、地点、连通关系、局部方向与通行限制。若时间线或地图缺失、事实截止落后，先按定稿正文重建或补齐再继续审计。不读取旧流程备份、临时目录或技能镜像作为小说事实。
3. 草稿、创作原料和未来章纲只代表候选或计划，不能覆盖定稿正文。未写规划只检查起点、前提和因果是否仍然成立，不能当成已经发生。
4. `2.4_文风.md` 只核对其中「本书要求」是否仍被正文遵守，不在本步骤进行逐句文风审稿。

#### 事实一致性检查

逐项检查以下内容，不得只搜索同名关键词：

1. 人物身份、称呼、位置、伤势、能力、资源、认知、目标和关系是否与定稿正文一致。
2. 世界规则、组织权限、力量体系、核心机制的触发条件、能力边界和代价是否被正文新增事实推翻或补充。
3. 已发生事件的时间、地点、因果、选择、结果和存亡状态是否在章纲与控制台中准确回写；时间线事实截止是否等于最新定稿，当前锚点与连续时间段是否与正文一致；地图中的区域、地点、连通关系、相对方向与通行限制是否与正文一致。
4. 正文已经新增或推进的角色、能力、关系、伏笔和阶段事实是否存在漏记；主角动态资产总账是否存在，当前概况是否与实际条目一致，事实截止是否与最新定稿一致。总账是否完整列出当前可调用能力或手段及其效果、限制、融合关系，资源、关键物品、凭证和其他动态资产能否按获得、消耗、归还、转移、失效对账；写明“当前无需要追踪的动态资产”时，正文和章纲是否确实没有需要跨章节核对的资产。旧状态、旧字数、旧章节号、过期待办和临时区块是否仍未清理；角色状态文件是否混入已退出当前工作集的人物或累计逐章依据；阶段角色文件是否混入已结算人物或在最新结果中累计逐章历史，活跃条目与低频归档是否重复，归档索引是否指向实际条目。
5. 是否把猜测、梦境、谎言、角色误判、未确认身份或未来计划误记为客观事实；也要检查已经确认的事实是否仍被写成未知。
6. 同一事实在预期、设定、大纲和控制台中是否出现互相冲突的并行版本，未写章纲的入口状态是否仍能承接最新定稿正文。

#### 剧情方向检查

1. 当前阶段的完成标志是否全部达成，不能只看章节数量或单个高潮是否结束。
2. 最近十章的实际路线是否仍在推进当前阶段目标，还是已经形成持续偏移、替代路线或新的主要矛盾。
3. 核心读者承诺、人物目标、关键关系与硬约束是否仍与总纲一致。
4. 长期未推进的关键任务或伏笔是否已经影响阶段成立，需要调整近端规划或阶段表述。

#### 处理审计结果

- 控制台或已定稿章节章纲存在明确漏记、旧状态或与正文一一对应的记录错误时，直接按定稿正文修正，并在交付中列明。
- 预期、稳定设定、总纲、未写规划与正文冲突，或修正需要追溯改动定稿正文时，先列出“定稿事实 / 冲突文件与原记录 / 影响 / 建议处理”，等待用户确认；不能静默覆盖。
- 不能确认哪一份内容正确时，保留不确定性并报告问题，不自行补设定。
- 审计没有发现问题时，在收尾交付中明确写出“全项目一致性审计完成，未发现需要修订的出入”及核对范围。- 审计发现阶段完成、持续偏移或近端安排已不适用时，另行输出“原计划 vs 实际走向 vs 后续影响”，等待用户确认后再修订规划。

短篇模式默认跳过全项目一致性审计，除非用户明确要求全面检查或调整尚未写的结局与方向。长篇在用户确认审计中需要修订的方案后，按下列分工执行：

- **真冲突处理**：只在正文与已定稿事实或稳定设定无法同时成立时，列出该处冲突、影响与建议，等用户确认后再改；用户不确认就不动。不得把正文正常新增的内容当成差异上报。

- **近端调整**：只改未写的十章章纲或未写章节的章纲，不改已定稿事实。
- **当前阶段调整**：阶段尚未完成时，只更新 `3-大纲/3.1_全书结构总纲.md` 的当前阶段或入口承诺，不补写未来阶段。
- **阶段切换**：当前阶段已经达到完成标志时，先按维护规则清理角色状态和阶段角色工作表，只保留明确带入下一阶段的动态状态与角色，再向用户说明实际收束结果并执行 `webnovel-outline`。由该技能归档已完成阶段摘要，并根据最新定稿事实共创下一个当前阶段；本技能不能自行推演并写入下一阶段。
- **设定事实调整**：先执行 `webnovel-setting-sync`，处理角色、规则、核心机制或世界设定的跨文件一致性，再回写受影响的大纲。

未触发时跳过本步骤，不输出虚构的“复盘结果”。
