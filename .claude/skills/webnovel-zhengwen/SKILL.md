# 番茄正文

## 目标与路径

每次只完成一章：读取当前事实，确定本章功能，整理章纲，写出草稿并先自查修正，再交付用户决定审查、润色、修改或定稿。

- 将本技能目录记为 `SKILL_DIR`，包含 `.agents/` 的项目根目录记为 `WORKSPACE_ROOT`。
- 小说文件从 `WORKSPACE_ROOT` 读取和写入。调用字数或句号换行检查脚本时，使用 `<SKILL_DIR>/scripts/` 下对应脚本的实际绝对路径，工作目录保持 `WORKSPACE_ROOT`。
- 文本表达、排版和人物真实性始终遵循项目根目录的 `AGENTS.md`；本技能不重复其中的语言规则。

## 文风执行优先级

`2-设定/2.4_文风.md` 是本书正文的具体文风依据，也是写草稿前必须重新读取的门槛。它决定正文“如何写”，不是完稿时可选的气氛参考；但不得与 `AGENTS.md` 的首遍可懂、信息落地和因果完整相冲突。

章纲与创作原料决定本章“写什么”；文风文件决定这些内容应当以什么语言、叙述和表达方式写成正文。剧情正确但没有按文风文件完成转写的草稿视为未完成，不能交付。

`AGENTS.md` 规定清楚、信息落地和避免生硬表达；`2.4_文风.md` 定义本书具体的语言、叙述和表达要求。两者必须同时满足，文风转写不得删除人物即时动机、判断依据、风险、代价或行动因果；疑似冲突时先保留解释并报告，不能以含蓄、留白或精简为理由省略必要信息。

用户最新创作原料优先决定事件、人物选择、结果、对白意图、具体动作、场景细节和表达重点，但不优先决定最终正文的句式与旁白措辞。

写草稿前必须将原料完整转写成符合 `2.4_文风.md` 的正文。具体应当如何处理叙述、对白、场景、动作、心理、转折和收束，只以文风文件的最新要求为准。

原料中的对白、动作、场景细节或整段文字，只有已经符合文风文件时才可直接采用；其余必须保留原意与事实后重新写成正文，不能因原料本身接近正文就跳过文风转写。

## 短篇模式覆盖

仅当用户明确创作短故事，或由 `webnovel-short-story` 调用并传入 `SHORT_STORY_MODE` 时使用：

- 用 `3-大纲/短篇方向大纲.md` 和 `3-大纲/短篇章纲.md` 代替长篇总纲和十章章纲文件。
- 跳过步骤 1；步骤 2 的本章方向从短篇方向大纲读取，章纲写入 `短篇章纲.md`。
- 默认单章 800-1500 字，用户指定范围优先；第一章将已确认的 `3-大纲/短篇导语.md` 放在正文开头。
- 步骤 3、步骤 4和草稿交付分支仍然执行，事实边界和定稿流程不变。

## 步骤 0：写作前置检查

1. 确保 `4-正文/` 存在，只创建缺失目录。
2. 长篇模式读取 `3-大纲/3.1_全书结构总纲.md`；短篇模式读取 `3-大纲/短篇方向大纲.md`。两种模式均读取 `2-设定/2.1_新书设定案.md`、`2-设定/2.3_主要角色设定表.md`、`2-设定/2.4_文风.md`；本章涉及已确认核心关系时，读取 `2-设定/2.3.2_核心关系.md` 的相关条目；本章出现、复用或结算阶段角色时，读取 `2-设定/2.3.1_阶段与功能角色记录.md` 的相关条目；本章涉及核心机制时，再读取 `2-设定/2.2_金手指设定.md`。
3. 首章读取预期、设定和当前模式方向文件中的开篇承诺；第 2 章起读取最近五章**定稿**（不足五章时取全部已有定稿）、`控制台/时间线.md`、`控制台/地图.md`、`控制台/角色状态.md`、`控制台/主角能力与资源.md`、`控制台/伏笔追踪.md`、`控制台/进度.md`。第一章定稿前时间线、地图和总账尚不存在属于正常情况，但第一次定稿时必须建立；已有定稿后任一文件缺失或事实截止落后，必须先按全部定稿重建。时间线是故事时间顺序、时长、期限和倒计时的事实边界；地图是区域、地点、连通关系、通行限制与未确认空间的当前事实边界；总账是主角动态资产的当前事实边界。本章材料首次出现需要跨章节核对的资产或空间事实时，只作为待定稿事实写入草稿，定稿后再更新对应控制台。
4. 长篇模式按本章章号确定所属十章章纲文件。第 1—10 章使用 `3-大纲/章纲_1-10章.md`，第 11—20 章使用 `3-大纲/章纲_11-20章.md`，后续依此类推；范围起始章为本章所在十章区间的首章，结束章为起始章加九。十章范围固定，不因剧情目标、阶段推进或实际收束情况改名。短篇模式使用 `3-大纲/短篇章纲.md`。当前模式的章纲不存在时，长篇依次执行步骤 1 和步骤 2；短篇跳过步骤 1，直接执行步骤 2。
5. 已有本章 `第X章_草稿_[标题].md` 或 `第X章_定稿_[标题].md` 时，先确认用户是要修改已有文本还是新写；不得覆盖已有稿件。同一章的标题在定稿前发生变化时，重命名现有草稿以反映最新标题，不另建一份重复草稿。
6. 用户确认的当前章纲或创作原料与现有设定、总纲或未写规划冲突时，定稿前不修改这些全局文档，也不提前执行 `webnovel-setting-sync`。写正文时按“用户最新确认的创作原料 > 当前章纲 > 现有设定与旧大纲”的顺序执行，并将实际差异写入本章“待定稿同步项”。只有冲突涉及已定稿正文或控制台中的既成事实时才停止并说明影响；用户明确确认追溯修改后再继续。

缺少会决定本章事实的材料时只问一次。不要为了补材料自行编造设定、角色关系、道具机制或前文事件。

## 步骤 1：十章章纲起点（仅长篇）

长篇每十章使用一个固定范围的章纲文件，不按剧情目标、阶段推进或实际收束情况提前结束、延长或重命名。文件名使用 `章纲_[起始章]-[结束章]章.md`，例如 `章纲_1-10章.md`、`章纲_11-20章.md`。

短篇模式跳过本步骤。长篇模式读取总纲中的当前阶段、上一章定稿和控制台状态；第 1 章尚无定稿正文时，使用已确认的开篇初始状态。当前十章章纲文件不存在时创建：

```markdown
# 章纲（第[起始章]—[结束章]章）

## 当前起点

[创建该十章范围时已经发生并确认的事实]
```

- **当前起点**只引用定稿正文、控制台或已确认开篇状态中的事实，不写预测、可能性和下一步安排。
- 不添加范围目标或其他替代性目标栏目。关键事件、关系推进、核心机制安排、伏笔、读者回报和节奏由每章章纲根据最新定稿事实即时决定。
- 当前十章范围最后一章定稿后，文件保持原名和原有内容。下一章进入新的十章范围时，再创建对应的新文件。

## 步骤 2：即时章纲

### 1. 先确定本章功能

判断本章主要属于开篇、承接、蓄势、兑现、关系/信息推进、转场或收束。功能决定开头强度、读者回报和结尾状态：

- 全书第一章前 200 字必须出现强压力、异常、冲突、反差或悬念。
- 承接章优先接住上一章留下的问题；常规、关系或转场章快速进入正在发生的事，不用背景、回忆或复述开场。
- 蓄势章可以不当场给大回报，但主角必须有观察、选择、准备或小幅推进，并让读者看到后续结算预期。
- 兑现章要让局面真实改变；收束章可以完成承诺、留下余波，不强行制造新钩子。

### 2. 取得本章思路

1. 先问用户是否已有本章思路。已有时以其为原料，不暗中改剧情。
2. 用户没有时，从长篇当前阶段方向、当前十章章纲的“当前起点”或短篇方向大纲、上一章结尾、未收伏笔、角色目标与状态、关系张力、外部压力和可用规则中，选择最相关的因素，提出 2-3 个不同方向。每个方向说明“本章推进什么、给读者什么、为什么现在发生”。
3. 用户选定方向后，可补充自己的展开。用户需要时再把方向扩成一段本章简介；不需要时直接进入建议。

### 3. 按需加载专项

- 本章核心是场景冲突、两难、反转或兑现时，读取 `conflict-design`。
- 本章核心是角色选择、关系拉扯或人物易写平时，读取 `character-vitality`。
- 本章存在战斗、追杀、对抗或斗法时，读取 `combat-writing`。

专项只补强命中的方面，不能覆盖已确认的本章方向。已在本次上下文读取过的专项直接沿用，不必重复读取。

### 4. 提出必要建议并整理

阅读用户原料后，只在确有价值时提出 0-3 条建议，说明改什么、为什么更好。用户采纳后才并入章纲；不得借建议私自新增设定或替换关键情节。

用户提供或修改本章材料后，按以下顺序即时更新当前章纲，不等章节定稿：

1. 将用户最新版详细材料写入“创作原料（定稿前临时保留）”。只整理标点、明显错字和阅读格式，不把具体事件、对白、动作、场景细节或表达意图压缩丢失。
2. 立即按最新版创作原料校正本章“剧情骨架”及其他受影响字段。校正只要求事件顺序、人物选择、结果和已确认事实一致；创作原料中的具体对白、动作拆分、走位、现场反应、环境细节和情绪节拍不必复写到剧情骨架。两者粒度不同不构成冲突。
3. 如当前章节要求与现有设定、总纲、十章章纲或未写规划冲突，只提醒具体差异。用户认可当前章节要求后，立即按其要求完成本章章纲更新，不重复阻塞，并将差异记入“待定稿同步项”。

创作原料不是已发生事实，也不是最终正文。当前章节讨论期间，以“用户最新确认的创作原料 > 当前章纲 > 现有设定、总纲、十章章纲与未写规划”的顺序处理。只有已定稿正文和控制台中的既成事实不能被静默覆盖；如需追溯修改，说明影响并取得用户确认。用户后续修改思路时，用最新确认版本替换对应内容，不累计互相冲突的旧版本。

章节定稿前，只允许更新当前章节的章纲条目、创作原料和草稿。不得因此修改设定、总纲、十章章纲的“当前起点”、控制台、其他章节章纲或其他全局资料，也不提前执行 `webnovel-setting-sync`。定稿后由 `webnovel-dinggao` 根据最终正文处理需要同步的全局资料。

### 剧情骨架的粒度与排版

- 剧情骨架只记录会改变后续局面的事件，例如人物进入或离开场景、目标或关系变化、重要信息获得或失去、资源或能力变化、冲突升级或结算。
- 剧情骨架必须使用 Markdown 有序列表，按正文发生顺序编号。每个列表项对应一次独立的局面变化。
- 同一场连续行动中，若中途没有新的选择、信息或局面变化，应合并为同一项，不按动作先后拆成多项。
- 每项只写发生什么、谁作何选择、造成什么结果。不展开具体台词、连续动作、招式过程、走位、现场反应、环境描写或情绪节拍，除非该细节本身改变后续剧情边界。
- 创作原料中的具体细节完整保留，但不逐项复写进剧情骨架。两者只要事件顺序、人物选择、结果和已确认事实一致即可。
- 用户补充细节时，只更新受影响的事件与结果，不把细节直接追加为新的剧情骨架列表项。

将确认内容写入长篇十章章纲文件或短篇 `3-大纲/短篇章纲.md`。使用以下结构，允许“无”或“不适用”，不要为了填模板硬塞爽点、伏笔或钩子：

```markdown
### 第 X 章 · [标题]

**本章功能与目标**
[本章推进什么、读者为什么继续读]

**剧情骨架**

1. [发生何事、谁作何选择、造成什么结果]

2. [下一次独立的局面变化]

**读者回报或压力**
[本章兑现什么，或为后续结算积累什么]

**伏笔与线索**
[埋下、推进或回收的内容]

**结尾状态**
[钩子 / 结算 / 情绪余波；说明下一章为何值得读或本段为何收口]

**待定稿同步项（定稿前临时保留）**
[当前章纲或创作原料与现有设定、总纲、十章章纲或未写规划的差异；没有时省略本节]

**创作原料（定稿前临时保留）**
> 本节不是已发生事实，也不是最终正文。写作时必须参考；与剧情骨架冲突时以用户最新确认的创作原料为准；与现有设定或旧大纲冲突时以当前章节要求为准，并记录待定稿同步项；只有已定稿正文和控制台既成事实不能被静默覆盖；章节定稿回写完成后删除。

[用户提供的最新详细思路；没有详细原料时省略本节]
```

旧章纲不再适用时，先说明与最新正文或用户要求的差异，再修订。通常等待用户确认章纲后写正文；用户明确授权直接写时，可以在说明章纲摘要后继续。

## 步骤 3：撰写草稿

1. 写草稿前重新读取本章章纲、“创作原料（定稿前临时保留）”，以及步骤 0 第 2、3 条中本章涉及的全部材料（含 `2-设定/2.4_文风.md`、设定案、角色表、核心关系、金手指、最近五章定稿、`控制台/时间线.md`、`控制台/地图.md`、其他控制台），作为写作时的事实边界与文风依据；不因步骤 0 已读取而省略。先用时间线确定上一章到本章的相对时段、已消耗的期限、可用时间窗口和不能精确换算的区间；再用地图确定本章可使用的区域、地点、已确认路线、局部方向和通行限制。正文出现跨日、等待、倒计时或具体时辰时，必须能挂接到已有时间锚点；正文出现转场、追逐、搜索、潜入或战斗空间时，必须能挂接到已确认地点或明确标为本章新发现，不能把未确认出口、距离或区域关系直接写成既定事实。材料间冲突时以用户最新确认的创作原料决定事件、人物选择、结果和保留细节，并先修正剧情骨架；若冲突涉及已定稿时间事实，先标出影响，不能静默改写时间线。当前章节要求与现有设定、总纲或未写规划冲突时，按当前章节要求写作并记录“待定稿同步项”，不提前修改全局文档；冲突涉及已定稿正文或控制台既成事实时，必须先说明影响。用场景、动作、对话、必要旁白和可见结果把已确认内容写成正文；人物为何行动或改变策略、依据什么判断、正在规避什么风险必须当下写清，不能只给动作让读者猜。拿不准解释是否需要时先保留。创作原料不是正文措辞的优先来源，必须按“文风执行优先级”完整转写；只有已经符合 `2.4_文风.md` 的具体对白、动作、场景细节或段落才可直接采用。不能因为原料本身接近正文而跳过文风转写，也不能因为剧情骨架经过压缩便无故遗漏用户明确保留的内容。
2. 生成正文时直接按句排版。每写完一个以句号结束的完整句，立即换行；对话中的句号后有右引号时，写完右引号立即换行。下一句不得接在同一行。对话与说话人动作或神态使用逗号、冒号连接时，可以按 `AGENTS.md` 的例外同行。不要先写成连续段落，再把换行留给步骤 4。
3. 按章节功能控制开头与结尾，承接上一章已知事实和状态，不复用旧章的比喻、意象或套话。
4. 长篇默认参考 2000-4000 字，短篇模式默认参考 800-1500 字；用户指定范围时优先。字数服务于完整场景和有效推进，不靠补背景、重复情绪或无效反应凑数。
5. 依照 `2-设定/2.4_文风.md` 和最近五章定稿正文（不足五章时取全部已有定稿）完成全章文风转写；首章没有定稿可参考时，以文风文件和设定为准。文风文件中指定的语言、叙述、对白、场景、动作、心理、转折和收束要求都必须落到正文里，不得把它降为“整体倾向”，但转写不得删除 `AGENTS.md` 要求当下写清的即时动机、判断依据、风险、代价和行动因果。
6. 从当前章纲取得章节标题，写入 `4-正文/第X章_草稿_[标题].md`。标题只写在文件名中，正文文件从第一句正文开始，不写 `# 第X章`、章节名或其他标题行。文件名中的半角禁用字符 `\ / : * ? " < > |` 使用合适的全角字符替换；没有自然替代时删除，并去掉标题末尾的空格或句点。写入后不立即交付，后续步骤始终使用该文件的实际绝对路径。

## 步骤 4：完稿校准

草稿完成后**必须先执行两项强制脚本校准**，再自查并直接修正其他可在不改变已确认剧情下解决的问题。这两项校准是**不得跳过的强制步骤**：无论你是否认为正文已经正确、无论章节长短、无论是否刚生成还是已多轮修改，都必须实际运行脚本，不得凭判断省略、合并到人工自查或声称“已检查无误”而跳过。运行后不检查退出码，不根据脚本输出再次处理或重跑，也不因此中止、询问用户或单独交付结果。

1. **句号换行自动校准**（强制）：在 `WORKSPACE_ROOT` 下执行：

   ```bash
   python "<SKILL_DIR>/scripts/check_sentence_linebreaks.py" --fix "<WORKSPACE_ROOT>/4-正文/第X章_草稿_[标题].md"
   ```

   将占位符替换为实际绝对路径和章节号。脚本直接修正句号或“句号加闭合引号”后仍有下一句正文的问题；拆句时保留一个空白行，中文引号内拆句时自动闭合并重新打开引号。后续审查继续处理仍然存在的排版问题。
2. **中文标点与引号自动校准**（强制，紧接上一步运行）：在 `WORKSPACE_ROOT` 下执行：

   ```bash
   python "<SKILL_DIR>/scripts/fix_quotes.py" --fix "<WORKSPACE_ROOT>/4-正文/第X章_草稿_[标题].md"
   ```

   将占位符替换为实际绝对路径和章节号。脚本按 `AGENTS.md` 统一修正英文半角句读、括号、破折号、省略号和错误引号，自动交换左右写反的引号对；处理 Markdown 文件时保护代码、链接、网址、路径、小数与列表标记。修复后仍不配对的引号只报告位置，由后续审查处理。
3. **字数**：在 `WORKSPACE_ROOT` 下执行：

   ```bash
   python "<SKILL_DIR>/scripts/count_chinese_words.py" X "<WORKSPACE_ROOT>/4-正文" --min-chars <参考下限> --max-chars <参考上限>
   ```

   将占位符替换为实际绝对路径、章节号和当前模式的参考范围：长篇默认 `2000` 至 `4000`，短篇默认 `800` 至 `1500`，用户指定范围优先。脚本只报告参考区间，不给正文判定“达标”或“不达标”；短于建议范围时，先检查是否缺少必要推进、结果或场景，不为达标硬补文字。
4. **章纲与阶段**：关键事件、章节功能、读者回报或蓄势预期、结尾状态是否按当前章纲落地；存在临时创作原料时，核对剧情骨架与最新版原料是否在事件顺序、人物选择、结果和已确认事实上一致，且剧情骨架没有被扩写成正文分镜。该粒度限制只约束剧情骨架，不约束正文；正文仍须呈现用户确认的关键对白、动作、走位、现场反应、情绪节拍以及必要的即时动机、判断、风险、代价和因果。核对用户明确保留的内容是否被无故遗漏；与现有设定、总纲或未写规划仍有差异时，确认已经记入“待定稿同步项”，不得把这种待定差异当成草稿错误而擅自改回旧版本。
5. **连续性**：先对照 `控制台/时间线.md` 核对本章时间词、跨日顺序、等待时长、期限、倒计时、固定时刻和当前时间窗口，再对照 `控制台/地图.md` 核对区域、地点、连通关系、局部方向、地形、监控、权限和未确认空间，最后核对人物、伤势、认知边界、因果、角色利益与前一章是否一致；正文没有精确天数时不得自行补算，未验证的空间关系不得自行补全。主角使用、获得、消耗、归还、转移或遗失的能力、资源、关键物品、凭证、权限和证据必须逐项对照 `控制台/主角能力与资源.md`，不能凭近期正文未提及便判断库存为零，也不能使用已经耗尽或不再持有的项目。
6. **核心机制**：本章涉及时，核对规则、限制、已知效果、能力承载和暴露风险，不给角色临场新增能力；章纲或用户原料新增动态资产变化时，只按已确认内容写入草稿，保留为待定稿事实，不提前修改动态总账。
7. **文风与可读性**：将 `2-设定/2.4_文风.md` 作为具体文风校准项，对照种子文风、最近五章定稿和 `AGENTS.md` 逐段复读，并直接重写不符合文风文件的文字。文风校准不能因为原料原句或通用规则已满足就判为通过，必须以文风文件列出的具体要求为准，在不改变事实的前提下完成转写；但不得删除首遍理解所需的即时动机、判断依据、风险、代价和行动因果。“解释腔”仅指事实已经写清后用答题式模板重复复述，或用大段设定讲解替代事件，不能把必要的直白解释判为问题。再修正重复、主语不清、动作无结果、人物反应失真和不合场景的细节；确认正文首行已经直接进入故事，没有重复文件名中的章号或标题。

输出自检卡，只报告实际检查与实际修正：

```markdown
## 完稿自检卡 · 第 X 章

| 检查项 | 结果 | 说明 |
| :--- | :--- | :--- |
| 字数 | XX 字 | 与用户要求或建议范围的关系 |
| 句号换行 | 已执行自动校准（必跑） | 已调用 `check_sentence_linebreaks.py --fix`；未运行则视为未完成本步骤 |

| 连续性 | 通过 / 已修正 | 时间、地图空间、认知、因果、状态与前章接续 |
```

## 交付与后续分支

草稿交付的最终回复必须包含以下内容，缺少任一项都不算完成：

1. 给出已校准草稿的实际路径，并明确当前仍是草稿。
2. 输出完稿自检卡，只报告实际检查和修正。
3. 在交付回复中**明确写出标点与引号校准的脚本结果**：读取 `fix_quotes.py --fix` 运行后打印的汇总行，告知用户「本章标点与引号共修复 N 处」（N 为脚本汇总行的实际数字；无需修复时写「本章标点与引号无需修复」），并列出脚本报告里仍无法自动判定的引号位置（如有）。
4. 最后一句直接询问用户选择以下一项：
   - **全面质检**：执行 `webnovel-review`。
   - **精修正文**：执行 `writing-optimization`。
   - **作者自行修改**：等待用户提供最新版，不根据旧草稿提前回写状态。
   - **确认定稿**：执行 `webnovel-dinggao`，以最新版正文完成转正、章纲回写和控制台更新。

用户作出选择前保持草稿状态，不得自动执行质检、精修或定稿，也不得只提示“确认后定稿”。
